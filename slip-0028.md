# SLIP-0028 : Transaction verification statements

```
Number:  SLIP-0028
Title:   Transaction verification statements
Type:    Standard
Status:  Draft
Authors: Petr Susil <petr.susil@satoshilabs.com>
Created: 2026-09-29
```

## Abstract

A transaction statement is a human-readable account of the security-relevant effects of the outputs of a transaction, such as the assets the payer sends or receives, which a wallet displays before it authorizes the transaction.
An attestation is a commitment to a statement, established by evidence which the wallet verifies under a trust anchor it holds.
The attestation is issued by a party or mechanism which the wallet trusts for that purpose, and which need not be the party that requested the payment.

## Motivation

A wallet can authenticate the destination and the amount of an output, but that does not establish what the output does.
Bitcoin `OP_RETURN` data and EVM calldata are transaction data which an address and an amount do not describe, and whose meaning depends on a protocol the wallet may not implement.
A wallet which cannot establish the effects of such an output can only present it as opaque data (*blind signing*) or refuse to sign it.

This specification defines a statement, which describes those effects in a form the wallet can display, and an attestation, which allows the verification of the statement to be performed elsewhere and checked by the wallet.
A statement in a payment request is trusted as far as the payment request signer is; an attestation establishes it independently.

A statement and its attestation are defined independently of any payment request, so that they can also be used when a transaction is signed without one.

## Statement

```
statement = summary || n || effect_1 || ... || effect_n
effect    = effectType || coinType || asset || bound || amount || party
```

* *summary* (length-prefixed UTF-8 string): a short description of the action by the party which makes the statement.
* *n* (CompactSize integer, minimally encoded): the number of effects, which MUST be distinct and in ascending lexicographic order of their encodings.
* *effectType* (1 byte): see below.
* *coinType* (4 bytes): the SLIP-0044 coin type of the asset, little-endian.
* *asset* (length-prefixed): the asset under *coinType*, empty for the native asset. For EVM coin types, the 20-byte contract address, followed for a non-fungible or multi-token contract by the 32-byte big-endian token identifier.
* *bound* (1 byte): 0x00 exact, 0x01 at least, 0x02 at most, 0x03 unbounded.
* *amount*: in the smallest unit of the asset, encoded as the amount of a requested output in [SLIP-0024](slip-0024.md); zero if unbounded.
* *party* (length-prefixed): an address, encoded as the address of a requested output in [SLIP-0024](slip-0024.md).

Length prefixes are CompactSize integers.

| *effectType* | Effect | Permitted *bound* |
| ------------ | ------ | ----------------- |
| 0x01 | *send*: the payer transfers the asset to *party*. | exact, at most, unbounded |
| 0x02 | *receive*: the asset is delivered to *party*. | exact, at least |
| 0x03 | *approve*: *party* may transfer the asset from the payer. | exact, unbounded |
| 0x04 | *delegate*: *party* obtains authority over the asset, or over every asset of the payer under *coinType* if *asset* is empty. | unbounded |

The bound limits the payer's loss, or for a receive the amount delivered. An approve or a delegate is stated as if it does not lapse.
A method MUST NOT apply to a payload with a security-relevant effect which these types cannot express. A statement with no effects states that the payload has none.

## Displaying a statement

A wallet which relies on a statement MUST display the summary and one line for each effect, in the order of the encoding.
The wording of each line is determined by the effect alone.
The summary MUST be displayed as a description provided by the party which makes the statement, separately from the effects, and the wallet MUST NOT present it as verified.

The canonical English rendering of an effect is:

| Effect | Rendering |
| ------ | --------- |
| send, exact | Send *amount* to *party* |
| send, at most | Send at most *amount* to *party* |
| send, unbounded | Send any amount of *asset* to *party* |
| receive, exact | Receive *amount* at *party* |
| receive, at least | Receive at least *amount* at *party* |
| approve, exact | Allow *party* to spend up to *amount* |
| approve, unbounded | Allow *party* to spend any amount of *asset* |
| delegate | Give *party* control of *asset*, or of the account if *asset* is empty |

A wallet MAY display a localized equivalent of the rendering.

The wallet formats *amount* and *asset* using asset metadata which it holds for the pair of *coinType* and *asset*. If the wallet holds no metadata for the asset, it MUST either display the asset identifier and the amount in the smallest unit, or refuse the statement.
An unbounded effect MUST be displayed in a way which distinguishes it from a bounded one.

The wallet MUST reject a statement which is malformed or non-canonical, has trailing data, or violates a constraint of [Statement](#statement).
The wallet MAY check an effect against facts which it establishes itself and MUST reject a statement which contradicts them.

## Attestation

An attestation is the concatenation of the following fields:

* *statement* (variable length): the attested statement, encoded as defined in [Statement](#statement).
* *verificationMethod* (4 bytes): 32-bit identifier of the verification method in little-endian byte order, see [Verification methods](#verification-methods).
* *attester* (length-prefixed binary string): identifier of the trust anchor under which the evidence for *attestationHash* is verified.
* *verificationData* (length-prefixed binary string): method-specific parameters and evidence.

## Payload

The *payload* is the requested outputs of the payment request where the attestation is used with one, and otherwise every output of the transaction being signed, in order. It is empty for a *state assertion*, an attestation which applies to no output.
The wallet computes

```
payloadHash = SHA256(output_1 || output_2 || ... || output_n)
```

from the transaction being signed, where *output*<sub>*i*</sub> is encoded as defined in [SLIP-0024](slip-0024.md), *Signature generation*.

## Verification context

The *verification context* encodes the facts outside the payload which can affect the statement:

```
verificationContext = coinType || nonce || methodContext
```

where *coinType* is the 32-bit little-endian SLIP-0044 coin type, which identifies the chain as defined in [SLIP-0024](slip-0024.md), *Coin type of EVM chains*;
*nonce* is a length-prefixed unpredictable challenge issued by the wallet;
and *methodContext* is defined by the verification method.

The wallet MUST derive the verification context from the transaction and the payment request, not from *verificationData*.
It MUST refuse a chain which has no registered coin type of its own, and MUST accept each nonce it issued at most once.

## Attestation hash

```
attestationHash = SHA256(b"\x53\x4c\x28\x41" || verificationMethod || attester || payloadHash || SHA256(verificationContext) || statement)
```

where the fields are encoded as in the attestation.
The wallet computes *attestationHash* itself; it is not part of the attestation.

## Evidence

*attestationHash* MUST be established by evidence in *verificationData* which the wallet verifies under a trust anchor it holds for the method. The wallet MUST NOT rely on an attestation unless the evidence establishes the value of *attestationHash* which it computed.

## Verification methods

A verification method determines both how the statement is derived and how the attestation is established; the same derivation established in different ways constitutes different methods.

A method MUST produce a *complete* statement, whose effects account for every *security-relevant effect* of the payload — any loss of the payer's assets, or any claim on them or on authority over them, now or later.

A statement depends on the payload alone (*interpretation*), on the payload executed against an observed state (*simulation*), or on an observation of mutable state (*dynamic state*);
where a statement mixes these, the strongest dependence applies. For a statement to be complete, an interpretation MUST bound each effect under the semantics the method covers
or mark it unbounded; a simulation MUST bound each effect by a condition which transaction validity or execution enforces or mark it unbounded; a dynamic state MUST identify the observed state.

A method MUST define:

* the payloads or state assertions to which it applies;
* the evidence in *verificationData* and the trust anchor which *attester* identifies;
* its *methodContext*, which MUST determine every other fact which can affect the statement and commit to any evidence from which one is established;
* how it establishes the effects of the statement.

## Use with a payment request

A wallet MAY require an attestation for a statement memo of a [SLIP-0024](slip-0024.md) payment request.
The nonce and *coinType* of the attestation are those of the payment request, its *statement* MUST be identical to the statement of the memo,
and the wallet MUST reject the payment request otherwise.
